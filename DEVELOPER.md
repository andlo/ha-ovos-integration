# Developer notes — ha-ovos-integration

## The idea

A real HA integration, not a bespoke webpage or per-add-on ingress page, fits how a HAOS user already expects to configure things: entities under Settings → Devices & services. OVOS skills already ship a `settingsmeta.json` describing their configurable fields — structurally the same thing HA integrations already do with their own config/options schemas, reused rather than reinvented.

Talks to the add-ons in [haos-ovos-addons](https://github.com/andlo/haos-ovos-addons). Open items and known gaps are tracked as [GitHub Issues](https://github.com/andlo/ha-ovos-integration/issues), not in this file.

## Shared configuration: polling, not file watching

Entities (language, units, API URLs, ...) read `/share/mycroft/mycroft.conf` via a `DataUpdateCoordinator` on a 30s poll interval, not a file watcher. Deliberate: `watchdog`-style file events fire from an OS thread outside HA's asyncio loop (a real source of subtle bugs to bridge correctly); every add-on writes via atomic rename (`jq > file.tmp && mv file.tmp file`), which a watcher would need to specifically handle; and the data itself (language, location, units) changes a handful of times a year, not something that needs instant reactivity. A `DataUpdateCoordinator` also means one file read per interval serves every entity regardless of count — adding more entities later doesn't change this cost either way.

## Config flow pre-fill sources

The shared-config flow pre-fills from `hass.config` directly: `language`+`country` combine into OVOS's `lang` format (a suggested default, not locked — a household running OVOS in a different working language than HA's own UI is a real case); `time_zone` maps directly (IANA names match); `latitude`/`longitude` copy directly; `unit_system.length` (`"km"` vs `"mi"`) maps to `system_unit`. City/state breakdown isn't available from HA Core and is left blank rather than guessed.

## Add-on API URLs: auto-discovered via Supervisor, not required by hand

See `supervisor_discovery.py` and [issue #4](https://github.com/andlo/ha-ovos-integration/issues/4) — the original design required a person to manually type each add-on's Supervisor-assigned hostname into its own `text.*` entity before anything depending on it (`autoconfigure`, skill install/listing) would work, a chicken-and-egg first-run problem for anyone starting from a clean install.

`__init__.py`'s `async_setup_entry` now calls `async_discover_addon_api_urls()` for whichever of the four URL keys are still empty, using the `SUPERVISOR_TOKEN` env var + a direct call to `http://supervisor/addons` (list) and `http://supervisor/addons/{slug}/info` (per-match, for the confirmed `hostname` field Supervisor already computes) — the same unofficial-but-widely-used pattern other community `custom_components` rely on for Supervisor access, not something requiring a special `manifest.json` permission (that's only for core-shipped integrations using `hassio`'s own internal Python helpers). Matching is by add-on slug suffix (`_ovos_core`, `_ovos_skills`, `_ovos_persona`, `_ovos_skills_extra`), not by display name, since the slug is the durable identifier.

Deliberately best-effort and additive only: no token present (a non-Supervisor install) or an add-on simply not found both just mean that key stays empty, same as before this existed — manual entry via the text entities is always still the fallback, and this discovery step never overwrites a value someone already entered or that a previous run already discovered.

## Skill management: one config subentry per skill

**Two-step add flow**, not one: a name-only dropdown first, then a confirmation step showing the selected skill's full description before install starts. A single dropdown with "Name — description" per option was confirmed, by screenshot, to wrap onto multiple lines and become hard to scan once the catalog had more than a handful of entries.

**A single subentry type**, not two. Splitting into `skill` (no reconfigure) and `skill_advanced` (has settings) was considered, to avoid showing a "Reconfigure" option on skills with no settings — rejected because `strings.json`'s `initiate_flow` key means every registered subentry type gets its own visible "Add [type]" menu entry, with no documented way to register one hidden from that menu. Showing "Skill" and "Skill (advanced)" as two confusing, similarly-named add options was worse than the alternative: a single type, and a clean "no settings available" abort message on skills without any.

**The confirmed-real `skill_id`, not the catalog's guess, is what a subentry gets created with.** The install flow polls the add-on's own job status and waits for the real result — the catalog's own `skill_id` field doesn't reliably match what a skill actually registers as at runtime, and creating a subentry with the wrong one silently broke settings lookups for every skill installed that way.

## Skill settings: live entities, not only a one-off reconfigure flow

See [issue #3](https://github.com/andlo/ha-ovos-integration/issues/3). `skill_settings.py` holds the shared field-inference logic (settingsmeta.json when present and exclusively checkbox fields, otherwise inferred from `settings.json`'s own value types) used by BOTH `skill_subentry.py`'s original one-off reconfigure flow and the new live entities below — one decision, not two copies that could drift.

`skill_settings_coordinator.py` polls every installed skill's own current settings on a 30s interval (separate from `OvosSharedConfigCoordinator`, which only ever reads the shared `mycroft.conf` — stored under its own `hass.data` key, `f"{entry.entry_id}_skill_settings"`, since every other platform already assumes `hass.data[DOMAIN][entry.entry_id]` IS the shared-config coordinator directly). `switch.py`/`number.py`/`text.py` each add one live entity per matching field, attached to the SAME device `sensor.py` already creates for that skill (by `DeviceInfo(identifiers=...)` alone, not a second device) — so a skill's version, its settings, and (see below) a link to advanced editing all live on one device page.

**Booleans, numbers, and plain strings only — never anything `skill_settings.SENSITIVE_NAME_HINTS` flags (name containing key/token/secret/password), and never nested objects/arrays.** The sensitive-field exclusion is a real security boundary, not a UX preference: an HA entity's state persists in history and is queryable via the API/logbook indefinitely, unlike a form value you type once and never see rendered back — turning a secret into standing, always-visible state would be a real ongoing exposure. Those fields, and anything with nested structure, stay reachable only through `skill_subentry.py`'s own reconfigure flow (which never creates persistent entities) or an external tool (see below).

**Discovery doesn't depend on a subentry existing.** First shipped keyed off `entry.subentries` only (skills added via "Add sub-entry → Skill") — confirmed wrong immediately: several skills installed directly against `ovos-skills`'/`ovos-skills-extra`'s own APIs (outside this integration's flow entirely, e.g. during `haos-ovos-addons`' own dev-VM testing) never got a subentry and so never showed up at all. `skill_settings_coordinator.py`/`sensor.py` now call each configured add-on's own `/skills` list directly (`skill_settings.list_installed_skills`) to discover every installed skill, and only consult `entry.subentries` afterward, separately, to look up a nicer display name and to scope an entity under `config_subentry_id` when one exists — never as a precondition for the entity/device existing. Considered creating a subentry programmatically for a skill discovered this way instead, but couldn't confirm a stable, documented Home Assistant Core API for adding a `ConfigSubentry` outside of a subentry flow; going the flow-independent-discovery route sidesteps that uncertainty entirely rather than risk shipping against an unconfirmed internal API.

**Grouping by source add-on: hub devices, not subentries.** Confirmed via community.home-assistant.io's own "Are there methods like async_setup_entry for a Config Subentry?" thread — there's genuinely no supported way to create a subentry outside of a subentry flow (no lifecycle hooks, no documented API), matching what the paragraph above already found independently. That same thread's own suggestion — "using devices (even ones without entities) seem to be able to do the same role" — is what `sensor.py`'s `_ensure_hub_device` does: an explicit `device_registry.async_get_or_create()` call (not a side effect of some entity's own `DeviceInfo`, since no entity belongs to the hub itself) for "OVOS Skills" / "OVOS Skills Extra", created lazily the first time a skill from that source is actually seen — never upfront, so an unconfigured or configured-but-empty add-on never gets a hub with nothing under it. Every skill device then sets `via_device` to point at its hub. This shows as "Connected via device" on the skill's own page and nests it under the hub on the Devices list — the closest supported equivalent to the subentry-based header grouping this integration's own added-via-flow skills get, not a pixel-identical reproduction of it.

**No "Core" hub (yet).** `ovos-core` hosts its own plugin skills too (e.g. `ovos-skill-boot-finished`, confirmed via its own boot logs during `haos-ovos-addons` testing), but its `api.py` has no `/skills`-equivalent endpoint to enumerate them — confirmed by reading the file directly, only `/health`, `/autoconfigure`, `/ask` exist. A "Core" hub would sit permanently empty without a companion change there first; not attempted in this pass.

**Superseded: auto-created real subentries, not hub devices, for the common case.** The hub-device approach above was built after concluding there was no supported way to create a subentry outside a subentry flow — that conclusion turned out to be based on incomplete research. Reading this project's own running Home Assistant version's `config_entries.py` directly (not just searching around it) showed `ConfigSubentryFlowManager` extends the exact same `data_entry_flow.FlowManager` base the regular config-flow manager does, so `hass.config_entries.subentries.async_init((entry_id, subentry_type), context={"source": ...}, data={...})` works the same way a normal flow's `async_init` does, just keyed by `(entry_id, subentry_type)` instead of a domain string. `skill_subentry.py`'s new `async_step_import` mirrors HA's own `SOURCE_IMPORT` convention (used by e.g. Zeroconf/DHCP discovery flows) for "create this entry directly, nothing to ask a person about" — `__init__.py`'s `_async_create_missing_skill_subentries` calls it once per skill the settings coordinator finds without an existing subentry, right after that coordinator's own first refresh and before platforms are forwarded, so by the time `sensor.py`/`switch.py`/etc. read `entry.subentries` those skills already have one.

This means every discovered skill now gets the same header-grouped placement on the integration's own page that a manually-added one always got — the actual UX problem the hub-device approach couldn't solve (that grouping is specifically a subentry feature; `via_device` only nests devices on the separate Devices list, not here). The hub-device code in `sensor.py` is left in place as a safety net, not removed: best-effort per-skill subentry creation could still fail or race, and a skill without one falls back to exactly the same hub grouping as before rather than losing its device/entities entirely.

**No `context={"source": "import"}` for subentries — confirmed by the first real attempt failing loudly.** `ConfigSubentryFlow.async_create_entry` hard-requires `self.source == SOURCE_USER` ("user"); any other context source raises `ValueError: Source is X, expected user` before the entry is even created — unlike regular `ConfigFlow`, which explicitly supports `SOURCE_IMPORT` for exactly this "create without asking a person" case. Subentries have no equivalent. `async_step_user` now detects the auto-import shape itself (payload contains `"skill_id"`, which the interactive `source_type`-dropdown path never sends) rather than routing through a separate `async_step_import` — the only way to satisfy the `SOURCE_USER` check while still allowing programmatic, no-form creation.

**Display name priority**: a subentry's own title (set at install time), otherwise a fresh lookup in `ovos-skills`' own `/catalog` (curated skills only — `ovos-skills-extra` has no catalog by design), otherwise `skill_settings.prettify_skill_id`'s best-effort cleanup of the raw `skill_id` (used for the majority of already-installed-before-this-existed skills, discovered with neither a subentry nor a curated-catalog match).

## Escape hatch: optional link to a self-hosted ovos-skill-config-tool

[ovos-skill-config-tool](https://github.com/OscillateLabsLLC/ovos-skill-config-tool) is a separate, third-party project — a generic `settings.json` editor with no type restrictions (handles nested objects/arrays, edits secrets in place) that this integration deliberately doesn't try to replicate; see the module docstrings above for why going further natively isn't the right call. `CONF_SKILL_CONFIG_TOOL_URL` is an optional text entity for wherever a person chooses to self-host it — not one of this project's own add-ons, and not auto-discovered via Supervisor for that reason (contrast `supervisor_discovery.py`, which only ever looks for `haos-ovos-addons`' own add-ons).

When set, it becomes each skill device's own `configuration_url` (see `sensor.py`) — HA's own native mechanism for "a device has more settings outside this integration," rendered as a plain "Visit" link on that device's page. Deliberately not a custom button entity for the same purpose: `configuration_url` already does this, and using it means one less thing to build and maintain.

## The conversation agent: skills-only, and now multi-turn-aware

`conversation.py`'s `OvosConversationAgent` forwards each utterance to `ovos-core`'s own `/ask`, deliberately with no persona fallback chained on top — see that file's own module docstring for why (stacking persona's own wait on top of `/ask`'s already made unmatched utterances noticeably slower, for a worse answer than a plain "I don't understand" in practice).

Genuine multi-turn dialogs (a skill's own `get_response()`, e.g. "what time should the alarm be?") are supported, not just one-shot answers, via `/ask`'s own `expect_response` field (see `ovos-core/DOCS.md`'s "Multi-turn dialogs" for how that's detected). When set, this agent returns `continue_conversation=True` in its `ConversationResult` — a real, existing Home Assistant Assist mechanism (`continue_conversation` + `conversation_id`, see [developers.home-assistant.io/docs/intent_conversation_api](https://developers.home-assistant.io/docs/intent_conversation_api)), not something invented here. Assist itself then automatically listens again and forwards the follow-up utterance back through `async_process` with the same `conversation_id` — no session tracking needed on this integration's own side, since the follow-up is simply sent through `/ask` again like any other utterance: OVOS's own bus (not this integration) is what routes it back to the specific skill still waiting on its own `get_response()` call.

Confirmed: `ConversationResult`'s own `continue_conversation` parameter is real and current (per Home Assistant's own developer docs example), and `async_process` (the method this agent already used, rather than the newer `_async_handle_message`) still supports it — HA's own docs describe that newer method as "backwards compatible" with the older one, not a breaking replacement. Not yet confirmed: a full round-trip through a real skill's own multi-turn flow end-to-end through Assist itself — blocked by this stack's own separate, already-documented intent-matching reliability issues (see `ovos-core/DOCS.md`'s "Intent pipeline"), not a flaw in this mechanism.

## Global OVOS settings, generically

`select.py`/`switch.py`/`text.py`/`number.py` cover `ovos-config`'s own top-level preference settings (temperature/windspeed/precipitation unit, time/date format, confirm-listening beep, plus `location`'s own sub-fields and timezone code) via two generic classes -- `OvosPreferenceSelect` and `OvosNestedText` -- rather than one near-identical class per setting. Only these simple, global preferences are exposed; nested plugin configs and internal wiring sections (`websocket`, `hivemind`, `log`, ...) deliberately are not -- editing those wrong risks breaking the shared bus every add-on in this project depends on, not just a preference. Defaults for each (see `const.py`'s own `DEFAULT_*` constants) match `ovos-config`'s real baked-in values exactly, confirmed via a real `ovos-core` add-on's `Configuration()`-backed `/config` endpoint, not guessed.

**A real bug found and fixed while building this**: `native_value` on any of these entities must read from `self.coordinator.data` (already fetched, safe to access synchronously) -- never call a helper that opens the shared file itself. Confirmed the hard way, a genuine "Detected blocking call to open... inside the event loop" warning on a real Home Assistant instance, traced to an early version of `OvosNestedText` that read the file directly from its own `native_value` property (entity state getters run synchronously in HA Core's own event loop; only the coordinator's own `_async_update_data`, already wrapped in `async_add_executor_job`, is allowed to do that I/O). `shared_config.py`'s own `write_nested_config_key` docstring documents this pattern going forward -- no read-side counterpart to that function exists on purpose.

All 13 attach to one shared device (`CORE_SETTINGS_DEVICE_ID`, "OpenVoiceOS Core Settings"), registered explicitly via the device registry in `__init__.py` -- confirmed missing was a real, reported gap: without it, these entities had nowhere to show up as a group on the integration's own page, unlike skills (their own subentry) or the `ovos-skills`/`ovos-skills-extra` hub devices (`sensor.py`'s own `_ensure_hub_device`). Same registration pattern as that function. **Debugging note for future reference**: a Home Assistant OS Supervisor install's own `docker logs` output can stop showing NEW lines partway through a genuinely successful startup (confirmed directly: the last visible line was consistently "found custom integration ovos/hacs" across many restarts, even on completely unrelated, already-known-good code) -- HA Core keeps running and finishes normally regardless, it just stops being visible via `docker logs` at that point. Check actual HTTP responsiveness (`curl` the real port -- confirmed this specific install serves on port 80, not the default 8123) or `.storage/core.device_registry`/`core.config_entries` directly, not `docker logs` completeness, to tell a real hang from this display quirk.

## Skills can't nest under one "Skills" umbrella -- confirmed, not a limitation of this integration

Raised directly: could `Alerts`/`Dad Jokes`/etc. be grouped under a single "Skills" section, the way `Core Settings` now gets its own section? Confirmed via Home Assistant's own architecture docs that config subentries don't nest (a device belongs to one subentry or the main entry, never a subentry-of-a-subentry), and confirmed via Home Assistant's own MQTT integration docs -- a mature, first-party example using the exact same subentry mechanism -- that "each \[MQTT\] subentry holds one \[MQTT\] device" is the *intended* pattern, not an MQTT-specific restriction. This project's own one-subentry-per-skill design already matches that convention exactly; there's no "put multiple devices in one subentry to group them" mechanism to switch to instead.

**What's offered instead**: every skill device gets the `OVOS Skill` label (`_async_label_skill_devices` in `__init__.py`), so they can still be found/filtered together elsewhere in HA (Settings -> Devices & services -> Devices, filtered by label) -- just not as a single collapsible section on this integration's own page, which will keep showing one section per skill.

**Implementation notes**: `device_registry.async_get_or_create` has no `labels` parameter at all (confirmed by reading its own signature directly) -- setting a label needs a separate `async_update_device(device_id, labels=...)` call using the device's real registry `id`, not its identifiers tuple. `label_registry.async_create` raises `ValueError` if a label with that name already exists (confirmed by reading its own source) -- unlike `device_registry`'s own idempotent `async_get_or_create`, so this always checks `async_get_label_by_name` first, the same "does one already exist" shape the `core_settings` subentry singleton above already needs.

## `OpenVoiceOS Core Settings` now has its own subentry, not just a device

Originally just a device registered via `config_entry_id` (see the section above this one). Moved to its own auto-created `core_settings` subentry (`core_settings_subentry.py`) after direct, reported feedback that the device looked out of place under Home Assistant's own generic "devices not belonging to a subentry" heading -- confirmed that heading is HA's own core UI string for config-entry-level devices, not something a custom integration can rename, but a device CAN move out from under it by belonging to its own subentry instead, the same way skill/persona/voice subentries already get their own named section.

Uses the exact same auto-import shape-detection entry point `skill_subentry.py`'s own `async_step_user` already documents (`ConfigSubentryFlow.async_create_entry` hard-requires `self.source == SOURCE_USER`, confirmed against this HA version's own `config_entries.py`) -- but with no interactive branch at all, since this subentry has no choices to make, ever.

**A real bug found and fixed while building this**: `hass.config_entries.subentries.async_init(...)`'s own return value does NOT have a `"subentry_id"` key -- confirmed the hard way, a genuine `KeyError: 'subentry_id'` on a real Home Assistant instance. Fixed by re-scanning `entry.subentries` for the newly-created entry (the same "does one already exist" lookup used to check beforehand) instead of trying to pull an id out of the flow result directly -- robust regardless of that result's own exact shape, which wasn't what was assumed.

**Debugging note, expensive to learn**: after this fix, a `homeassistant.helpers.frame` WARNING appeared -- "assigns an existing device to a different config subentry... this silently moves the device" -- for the one device that existed under the OLD (pre-subentry) registration method being moved to the new subentry-based one. Confirmed this is a one-time migration artifact, not an ongoing problem: the warning itself says it "will stop working in Home Assistant 2027.8.0", meaning it currently still works, just deprecated. Chased this further than necessary before realizing it was benign -- a warning is not a crash, and `curl`ing the real port already confirmed the integration was working correctly regardless.

## Adding new global settings: a table row, not a new class

Raised directly: could exposing more of `ovos-config`'s own deeper settings be built so a FUTURE one is less work each time, rather than hand-writing a new class per setting? `const.py`'s own `CORE_NUMBER_SETTINGS`/`CORE_SWITCH_SETTINGS`/`CORE_SELECT_SETTINGS`/`CORE_TEXT_SETTINGS` tables are the answer: each row is `(path_parts, name, icon, default, ...)`, and each platform file's own `async_setup_entry` just iterates its table and instantiates one already-generic class per row (`OvosNestedNumber`/`OvosNestedSwitch`/`OvosNestedSelect` in their own platform files; text reuses the already-generic `OvosNestedText` directly). Adding the 24th setting is one new line in a table, not a new class or a new `add_entities` call.

Covers `intents.adapt`/`intents.padatious` (Adapt/Padatious matching confidence thresholds and a few behavior flags), `intents.common_query` (timeouts, reranker plugin), and `intents.OCP` (media-playback behavior) -- 23 settings total, confirmed against `ovos-config`'s own default `mycroft.conf` directly (see `ovos-core/DOCS.md`'s own investigation for how that file's full structure was mapped out). Deliberately NOT `intents.pipeline` itself -- that's the ordered 13-stage matching sequence, a list defining order, not a leaf value, and doesn't fit any of these entity types.

**A real type bug caught before it caused a problem**: `intents.OCP.playback_mode`'s own real default is the int `0`, not the string `"0"` -- confirmed by reading `ovos-config`'s own default `mycroft.conf` directly. `SelectEntity`'s own `options`/`current_option` contract is always strings, so `OvosNestedSelect` stringifies for display but casts back with `type(self._default)` when writing -- without this, picking an option would silently rewrite the setting as a string, and OVOS's own code comparing against the literal int (`if playback_mode == 0`) would then never match again.

**A signature-order mismatch worth documenting**: `OvosNestedText`'s own existing constructor is `(path_parts, default, name, icon)` (already used and working for the location fields above), but `CORE_TEXT_SETTINGS`' own rows are `(path_parts, name, icon, default)` -- kept consistent with the other three tables rather than matching that one class's own argument order. The one `add_entities` call that uses `CORE_TEXT_SETTINGS` reorders explicitly (`row[0], row[3], row[1], row[2]`) instead of changing `OvosNestedText`'s own signature, which the location fields already depend on working exactly as it is.

## Editing list-type settings (`intents.pipeline`, skill white/blacklists) -- no reordering widget exists, confirmed

Raised directly: could `intents.pipeline`'s own stage order (or the various skill whitelist/blacklist settings) be exposed too? Confirmed by reading Home Assistant's own `selector.py` directly: `SelectSelectorConfig`'s own fields are `options`, `multiple`, `custom_value`, `mode`, `translation_key`, `sort` -- no `reorder` field. The `reorder=True` capability HA's own `EntitySelector`/`DeviceSelector`/`AreaSelector` offer (confirmed via HA's own `group` integration's config flow, which uses it) only applies to selectors that pick real HA registry objects -- there's no equivalent for a plain list of named strings like pipeline stage names or skill_ids.

**What's built instead**: `OvosNestedList` (text.py) -- a single text field holding the whole list as a plain comma-separated string, edited by typing rather than dragging. Covers `intents.pipeline` (stage order, genuinely reorderable this way) plus `skills.blacklisted_skills`, `skills.converse.converse_whitelist`/`converse_blacklist`, `skills.fallbacks.fallback_whitelist`/`fallback_blacklist` -- all in `const.py`'s own `CORE_LIST_SETTINGS` table, same one-row-per-setting pattern as the other three tables.

**Deliberately no content validation**: raised directly and agreed -- neither `intents.pipeline`'s own valid stage names nor real skill_ids are a fixed set this integration could safely hardcode a check against. OVOS itself can add, remove, or rename pipeline stages over time, and skills are installed/removed freely; hardcoding a validation list here would work against this whole feature's own stated goal (a future setting/value needing no new code). `OvosNestedList` only does basic hygiene -- trimming whitespace, dropping empty entries from a stray comma -- real validation of the CONTENT is left to OVOS itself when it actually reads the config, the same as if it had been hand-edited in `mycroft.conf` directly.

Also added, while re-reading `skills.converse`/`skills.fallbacks` for this: 7 more simple leaf settings across the existing three tables (`converse.timeout`, `converse.max_activations` in `CORE_NUMBER_SETTINGS`; `converse.cross_activation`/`cross_deactivation` in `CORE_SWITCH_SETTINGS`; `converse.converse_mode`/`converse_activation`, `fallbacks.fallback_mode` in `CORE_SELECT_SETTINGS`) -- no new code needed for these either, confirming the table-driven design's own point.

## Relationship to the other repo

[haos-ovos-addons](https://github.com/andlo/haos-ovos-addons) — the Supervisor add-ons this integration configures. See in particular `ovos-skills`/`ovos-skills-extra` (the skill install APIs this integration's subentries call) and `ovos-persona` (the solver-configuration API).
